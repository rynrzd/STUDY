Règle n°1 - ne pas mentir sur l’état du produit
Claude ne doit jamais écrire « tout fonctionne », « aucun bug », « sécurisé » ou « terminé » sans avoir exécuté les vérifications
correspondantes. Un point non testé doit être marqué NON VÉRIFIÉ avec la raison. Un build réussi ne prouve pas que les
parcours fonctionnent.
Règle n°2 - conserver ce qui fonctionne
Avant modification : inventaire des routes, composants, tables, policies, rôles et parcours existants. Ne pas supprimer/recréer
une fonction saine juste pour simplifier le développement. Toute migration destructive doit être explicitée et réversible.

5. Assistant de rentrée - import établissement
Objectif concret
Un lycée possédant 10 fichiers de classes doit pouvoir les déposer, voir 10 classes proposées avec leurs élèves, corriger les
anomalies, valider une seule fois, puis obtenir les comptes et affectations. Aucune création définitive pendant l’analyse.
5.1 Dépôt
ACTION UTILISATEUR : Admin ouvre /admin/import et dépose plusieurs XLSX/CSV.
CE QUI DOIT SE PASSER : Liste des fichiers, taille, état de lecture, nombre de lignes détectées. Bouton Continuer désactivé tant
que parsing en cours.
ERREURS / CAS LIMITES : Fichier corrompu/trop gros/type interdit : erreur sur ce fichier sans crash global.
TEST DE RECETTE : Tester 10 fichiers valides + 1 invalide.
5.2 Détection des classes
ACTION UTILISATEUR : Le système analyse noms de fichiers et colonnes.
CE QUI DOIT SE PASSER : Proposer une classe par fichier si cohérent, ou regrouper via colonne Classe/Division/Groupe.
Afficher source de la détection et permettre correction.
ERREURS / CAS LIMITES : Ne jamais décider silencieusement en cas d’ambiguïté.
TEST DE RECETTE : Fichier « liste.xlsx » sans colonne classe : demander mapping/nom de classe.
5.3 Mapping des colonnes
ACTION UTILISATEUR : Admin vérifie Nom, Prénom, Classe, Email, identifiant éventuel.
CE QUI DOIT SE PASSER : Afficher colonne source > champ AvecStudy, exemple de valeur et statut sûr/à confirmer/non
reconnu.
ERREURS / CAS LIMITES : Ne pas créer une personne si Nom/Prénom requis manquent ; ne pas transformer une colonne
arbitraire en email.
TEST DE RECETTE : Tester « Nom élève », « NOM », « surname », cellule vide et colonnes inconnues.
5.4 Normalisation
ACTION UTILISATEUR : Continuer.
CE QUI DOIT SE PASSER : Nettoyer espaces/casse pour comparaison, normaliser noms de classes sans perdre la valeur
affichée, valider emails, détecter homonymes/doublons.
ERREURS / CAS LIMITES : Ne pas fusionner deux élèves uniquement parce que nom/prénom identiques.

8. Documents - stockage et compréhension
8.1 Organisation
À CONSTRUIRE / MODIFIER : Tout document doit être rattaché à établissement + contexte
(classe/matière/chapitre/séance/devoir). Afficher nom lisible, type, taille, auteur, date et emplacement.
INTERDIT : Pas de dossier fourre-tout ni bucket public par facilité.
CRITÈRE DE VALIDATION : Un élève retrouve un document depuis la séance correspondante et ne peut ouvrir celui d’une autre
classe.
8.2 Import de documents
À CONSTRUIRE / MODIFIER : Accepter fichiers autorisés, valider côté serveur, uploader avec état de progression/erreur.
Prévisualisation quand possible.
INTERDIT : Ne pas prétendre « comprendre » automatiquement le contenu d’un PDF/Word si aucun parseur fiable n’est
réellement implémenté. Ne pas classer automatiquement avec certitude en cas d’ambiguïté.
CRITÈRE DE VALIDATION : Si une fonction de lecture/classement existe, afficher ce qui a été détecté et demander confirmation
lorsque la confiance est insuffisante.
8.3 Sécurité fichiers
À CONSTRUIRE / MODIFIER : Stockage privé, contrôle d’accès serveur/RLS, URL signée temporaire si nécessaire.
INTERDIT : Pas de lien permanent public vers documents scolaires privés.
CRITÈRE DE VALIDATION : Copier l’URL et l’ouvrir déconnecté/autre classe : accès refusé.
9. Admin lycée - écrans de gestion
 Dashboard : uniquement informations utiles (classes, élèves, professeurs, imports récents, erreurs à traiter). Pas de faux KPI.
 Classes : recherche, effectif, professeurs/matières affectés, ouvrir une classe, archiver selon droits.
 Élèves : recherche nom/prénom/identifiant, classe, état du compte, changer classe, reset accès, désactiver. Toute action
destructive confirmée.
 Professeurs : recherche, matières, classes, affectations, état compte.
 Imports : historique avec statut, auteur, date, fichiers, résumé et erreurs.
 Année scolaire : classe active rattachée à une année ; archivage logique pour éviter le mélange entre rentrées.

10. Sécurité - tests offensifs obligatoires
□ IDOR : changer chaque ID dans URL/API pour classe, séance, devoir, document, élève, prof, import, fil entraide.
□ Isolation établissement A/B : admin A, prof A, élève A ne doivent obtenir aucune donnée B.
□ RLS : tests positifs et négatifs exécutés avec vrais rôles de test.
□ Auth : session expirée, déconnexion, reset, compte désactivé, accès admin sans rôle.
□ Uploads : extension trompeuse, nom étrange, taille excessive, URL après déconnexion.
□ Secrets : rechercher service role/tokens/secrets dans bundle client, dépôt, logs et réponses.
□ Headers : CSP/permissions/referrer/HSTS selon déploiement ; cookies HttpOnly/Secure/SameSite adaptés.
□ Rate limit : login/reset/import/endpoints coûteux si exposés.
□ Logs : aucune donnée sensible ou mot de passe provisoire dans les logs.
11. Responsive et accessibilité
□ Tester 375, 390, 430, 768, 1024, 1280, 1440 px.
□ 0 overflow horizontal critique ; 0 texte tronqué non volontaire ; boutons touch >= zone confortable.
□ Navigation mobile dédiée pour l’élève ; admin/prof restent utilisables mais optimisés ordinateur.
□ Focus visible, navigation clavier, labels de formulaires, messages d’erreur reliés aux champs.
□ Contrastes lisibles ; le rose n’est jamais le seul indicateur d’état.
□ prefers-reduced-motion respecté ; aucune animation indispensable à la compréhension.
12. Performance et robustesse
□ Mesurer les routes principales avant/après. Ne pas inventer un gain.
□ Landing : JS minimal ; fragments marketing légers ; lazy-load hors écran.
□ Listes de centaines/milliers : pagination/recherche serveur, pas de rendu massif inutile.
□ Imports : progression, reprise/idempotence, protection double-submit, messages exploitables.
□ Vérifier requêtes N+1 et index des clés établissement/classe/utilisateur/affectation.
□ Loading/empty/error/retry cohérents sur tous les parcours critiques.
□ Aucune dépendance lourde ajoutée sans justification.

15. Definition of Done - blocage de livraison
□ Import multi-classes réel passe et le résultat correspond à la prévisualisation.
□ Réimport ne crée pas de doublons inattendus.
□ Professeurs voient uniquement leurs affectations.
□ Élèves voient uniquement leur classe et les contenus publiés.
□ Documents privés résistent aux accès croisés.
□ Publication professeur -> apparition élève ciblé vérifiée E2E.
□ Landing desktop/mobile respecte la direction sans gros dashboard compressé.
□ Typecheck/lint/build/tests critiques passent.
□ Smoke test production exécuté si l’environnement est accessible.
□ Tout point non testé est explicitement déclaré ; aucun résultat n’est inventé.
Important
On ne peut pas garantir mathématiquement « zéro bug ». L’objectif de livraison est : aucun bug bloquant connu dans les
parcours testés, aucun échec de sécurité connu dans les tests définis, et transparence complète sur ce qui n’a pas pu être
vérifié.
